# InfuraSaito Roadmap: PR Breakdown

> **For agentic workers:** This is the index. Each PR gets its own detailed, bite-sized plan in this folder (`2026-10-16-prNN-<name>.md`), written just before that PR starts so it matches the code as it is then. Execute one PR at a time: branch from up-to-date `main`, implement, push, open the PR, merge, then move on.

**Goal:** Take InfuraSaito from a working demo to a hardened forecasting service with alerts, anomaly detection, background training, persistence and dashboards.

**Ground rules for every PR**
- Branch from current `main`: `git switch main && git pull && git switch -c <branch>`.
- TDD: write the failing test first (from PR 1 on, both test suites exist).
- CI must be green before merge: Go unit, Python unit and integration jobs.
- Update `README.md` (endpoints, env vars) when behaviour changes. `report.tex` is local only; update it too if it describes the changed behaviour.
- One concern per PR. If a PR grows past about 400 changed lines (excluding generated files), split it.

**Verified facts this plan relies on (2026-10-16)**
- Prophet 1.1.6 breaks with `cmdstanpy` 1.3.0 and `pandas` 3.x (`'Prophet' object has no attribute 'stan_backend'`). It works with `cmdstanpy==1.2.5`, `pandas==2.2.3`, `numpy==2.2.6`.
- Prophet rejects timezone-aware `ds` values. Go sends RFC3339 UTC (`...Z`), so `/predict` with real history currently fails with HTTP 500. CI never noticed, because the integration test only hits the cold-start fallback.
- Go 1.22 is not installed locally. Build and test with Docker: `docker run --rm -v "$PWD/go-api:/src" -w /src golang:1.22 go test ./...`.

## PR 1: Test foundation, and fix the real forecast path
**Branch:** `test/foundation` · **Detailed plan:** `2026-10-16-pr01-test-foundation.md`
**Scope:** pin Prophet's transitive dependencies; normalise `ds` to naive UTC in `model.py`; pytest suite (`ai-service/tests/`); Go unit tests with fake Prometheus and AI servers (`go-api/*_test.go`); CI jobs `go-unit` and `py-unit` that the integration job needs; an integration step that runs a real Prophet forecast through the AI service.
**Acceptance:** `go test ./...` and `pytest` pass locally and in CI; the integration job proves `/predict` returns predictions for UTC history.

## PR 2: Hardening (timeouts, input limits, shared metric map)
**Branch:** `fix/hardening` · **Depends:** PR 1
**Scope:**
- `go-api/httpclient.go`: one `http.Client` with timeouts, used by `prometheus.go` and `ai_client.go`. `PROM_TIMEOUT` defaults to 10s, `AI_TIMEOUT` to 60s.
- `horizon_minutes`: reject values below 1 or above 10080 (7 days) with 400 in Go. Mirror it in Pydantic (`Field(gt=0, le=10080)`).
- `/api/v1/metrics/current` accepts `metric` and uses the same metric map, with an instant-query variant per metric. Unknown metric returns 400.
- `queryPrometheus`: guard `Value` length to avoid an index panic.
**Acceptance:** tests for each limit and timeout (use a fake server that sleeps longer than a test-sized timeout).

## PR 3: More metrics (disk, network, load)
**Branch:** `feat/more-metrics` · **Depends:** PR 2
**Scope:** extend the metric map in one place (`go-api/metrics.go`, moved out of `handlers.go`) with `disk` (percent used of `/`), `network_rx` and `network_tx` (bytes/s), and `load1`. Each entry has a range query and an instant query. README table of metrics.
**Acceptance:** table-driven test asserting every metric has both queries; the integration test calls `/forecast` for each metric and gets 200.

## PR 4: Multi-instance support
**Branch:** `feat/multi-instance` · **Depends:** PR 3
**Scope:** parse series labels (`PromResponse.Result[].Metric`). New optional `instance` query parameter on `/forecast` and `/metrics/current`. With one series and no `instance`, use it. With several series and no `instance`, return 400 listing the available instances. New `GET /api/v1/instances`.
**Acceptance:** tests with a fake Prometheus returning two series cover the select, error and listing paths.

## PR 5: Compose healthchecks and pinned images
**Branch:** `chore/compose-health` · **Depends:** PR 1
**Scope:** healthchecks for prometheus (`wget -qO- localhost:9090/-/ready`), node-exporter, ai-service (Python urllib on `/health`) and go-api (`wget` on `/healthz`). `depends_on: condition: service_healthy`. Pin `prom/node-exporter:v1.8.2` and `alpine:3.20` in both compose files and the Go Dockerfile. `clean_setup.sh` uses `docker compose up --wait`.
**Acceptance:** `docker compose up -d --wait` returns only when all services are healthy; CI green.

## PR 6: API-key auth and rate limiting
**Branch:** `feat/auth-ratelimit` · **Depends:** PR 2
**Scope:** `go-api/middleware.go`. If `API_KEY` is set, `/api/*` requires `X-API-Key` (constant-time compare) and returns 401 otherwise. `/healthz` stays open. A global token bucket (`golang.org/x/time/rate`, `RATE_LIMIT_RPS` defaulting to 10, burst 20) returns 429 when exceeded. Both are off by default locally; the CI integration test runs with a key set.
**Acceptance:** middleware unit tests for missing, wrong and correct keys and for rate exhaustion.

## PR 7: Background training and model cache
**Branch:** `feat/background-training` · **Depends:** PR 4
**Scope:**
- AI service: `POST /train {metric_name, instance, history}` fits and caches a model keyed by `(metric, instance)` in a lock-protected dict. `POST /forecast {metric_name, instance, horizon_minutes}` predicts from the cache and returns 404 if no model exists. `/predict` (train and predict) stays as a fallback.
- Go: `go-api/scheduler.go` goroutine. Every `TRAIN_INTERVAL` (default 15m), for each metric and instance with at least 2 points, fetch history and call `/train`. `forecastHandler` tries `/forecast` first and falls back to `/predict` on 404.
**Acceptance:** Python tests for cache hit and miss and for concurrent training; Go tests for the fallback order using a fake AI server; measured `/forecast` latency on a cached model under 500ms.

## PR 8: Circuit breaker on Go → AI calls
**Branch:** `feat/circuit-breaker` · **Depends:** PR 7
**Scope:** wrap the AI client in `sony/gobreaker` (trips after 5 consecutive failures, 30s open). When open, `/forecast` returns 503 with `Retry-After`. Breaker state is logged on change.
**Acceptance:** test where a fake AI server returning 500 trips the breaker and later calls fail fast without reaching the server.

## PR 9: Threshold-crossing forecast endpoint
**Branch:** `feat/threshold` · **Depends:** PR 7
**Scope:** `GET /api/v1/forecast/threshold?metric=&instance=&threshold=&horizon_minutes=` returns `{will_cross, expected_at, possible_at}`: the first prediction whose `value` (expected) or `upper` (possible) reaches the threshold. Pure function `firstCrossing(preds, threshold)` in `go-api/threshold.go`.
**Acceptance:** table-driven tests for `firstCrossing` (never, expected, possible-only, first point); handler test.

## PR 10: Alerting job and webhook
**Branch:** `feat/alerts` · **Depends:** PR 9
**Scope:** alert rules from `ALERT_RULES` (JSON, e.g. `[{"metric":"cpu","threshold":80,"horizon_minutes":60}]`) and `ALERT_WEBHOOK_URL`. The scheduler evaluates rules after each training cycle and POSTs a JSON payload (Slack-compatible `text` field) when a crossing is predicted. Duplicates are suppressed per rule and instance until the forecast clears.
**Acceptance:** tests for rule parsing, firing, deduplication and clearing using a fake webhook server.

## PR 11: Anomaly detection
**Branch:** `feat/anomalies` · **Depends:** PR 7
**Scope:** AI service `POST /anomalies {metric_name, instance, history}` uses the cached model's in-sample `yhat_lower` and `yhat_upper` and returns the points outside the band, with their deviation. Go `GET /api/v1/anomalies?metric=&instance=&window_minutes=60`. Optional: send anomalies through the PR 10 webhook.
**Acceptance:** Python test with an injected spike in synthetic data that is flagged, while normal points are not.

## PR 12: Forecast storage and accuracy
**Branch:** `feat/forecast-storage` · **Depends:** PR 7
**Scope:** add a `postgres:16` service (with healthcheck) to compose. `go-api/store.go` uses `pgx` and an embedded migration creating `forecasts(id, metric, instance, created_at, target_time, value, lower, upper)`. Each scheduled forecast is stored. `GET /api/v1/forecast/accuracy?metric=&instance=&days=7` returns MAPE and band coverage (share of actuals inside `[lower, upper]`).
**Acceptance:** store tests against a real Postgres (CI service container); accuracy math tested as a pure function.

## PR 13: Self-monitoring
**Branch:** `feat/self-metrics` · **Depends:** PR 7
**Scope:** Go `/metrics` via `prometheus/client_golang`: request count and latency by route and status, AI call duration, breaker state, last training time. Python `/metrics` via `prometheus_client`: training duration, number of cached models. Add both as scrape jobs in `infra/prometheus.yml`. Scheduled forecasts are exported as gauges (`infurasaito_forecast_value{metric,instance,bound}`) for PR 14.
**Acceptance:** tests that the metrics exist and increment; Prometheus targets page shows all jobs up.

## PR 14: Grafana dashboard
**Branch:** `feat/grafana` · **Depends:** PR 13
**Scope:** `grafana/grafana:11.x` in compose with a provisioned Prometheus datasource and dashboard JSON (`infra/grafana/`). Panels: actual vs forecast band per metric, threshold lines, anomaly markers, service health and latency.
**Acceptance:** `docker compose up` shows the dashboard with live data at `localhost:3000`, with no manual setup.
